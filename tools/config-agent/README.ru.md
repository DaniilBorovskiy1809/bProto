# Агент применения конфигураций

Панель обращается к одному заданному оператором HTTPS-агенту по mTLS.
На сервере панели задаются BPROTO_CONFIG_AGENT_URL, BPROTO_CONFIG_AGENT_IDENTITY
(PEM сертификата и ключа клиента), BPROTO_CONFIG_AGENT_CA. Адрес назначения
не принимается из браузера. Endpoint требует авторизации администратора.

Запуск: `python3 tools/config-agent/agent.py /etc/bproto/agent.json`.
Полный пример настроек приведён в README.md. validate, reload, health — массивы
аргументов команд, заранее установленных оператором. Командная оболочка не
вызывается. Валидатор получает путь кандидата в BPROTO_CANDIDATE_CONFIG и должен
проверить реальную конфигурацию сервиса. Health обязан проверять работу туннеля.
Лимит каждой команды — 15 секунд.

Применение: проверка версии 1 → приватный временный файл → валидация → сохранение
предыдущего файла → атомарная замена → перезапуск → health. При сбое восстанавливается
старый файл и повторяются перезапуск/health. Неудача восстановления явно сообщается.
Исходная конфигурация должна быть установлена заранее. В панели есть
Apply/Health/Rollback; применение прерывает подключения настроенного TLS-сервиса.

Семь Python-тестов проходят, покрытие — 75%. Проверены откат, валидация, права 600
и реальное mTLS-соединение с отказом клиенту без сертификата. Команды сервиса
в транзакционных тестах подменены: развёртывание systemd и полный e2e через панель
пока не проверены.

Используйте отдельную сеть управления, выделенный клиентский CA и один процесс
агента. Нет межпроцессной блокировки и журнала восстановления после аварии.
Все клиентские сертификаты доверенного CA имеют право применять настройки.
Конфигурации и резервные копии могут содержать секреты. Файлы имеют права 600:
учётная запись сервиса должна иметь доступ. Автоустановка и ротация сертификатов
отсутствуют. Агент не гарантирует обход РКН.

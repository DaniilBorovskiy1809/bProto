# Обязательный ECH на клиенте — экспериментально

Native HTTP/3 и Android QUIC поддерживают ECH через rustls и AWS-LC HPKE.
Конфигурация ECH публичная, но должна быть получена от владельца сервера по
доверенному каналу. Автоматическое получение HTTPS DNS RR пока отсутствует.

В quic-профиле задаются ech.mode = required, ech.config_list (base64 ECHConfigList)
и ech.expires_unix_secs. Пример и команды — в README.md. Декодированная длина:
2..4096 байт. Истёкший срок отклоняется до подключения. Rust проверяет структуру
и поддерживаемые криптографические параметры до отправки ClientHello.

Отсутствие ech отключает ECH. Если ech указан, поддерживается только required.
Режимы optional/grease, ECH внутри TLS/WSS и корневое поле ech отклоняются,
чтобы требование не потерялось молча. Панель экспортирует ECH в Android QUIC-ключ;
это не включает ECH на сервере.

Для native helper используются BPROTO_ECH_CONFIG (файл с бинарным списком),
BPROTO_ECH_EXPIRES (Unix seconds) и прежний BPROTO_BRIDGE_TOKEN.
Сборка: cargo build --locked -p vpn-core --features ech --example h3_bridge.
JNI включает feature ech. Без неё требование ECH отвергается.

Проверка реальных байтов ClientHello показала публичное имя и расширение ECH,
без скрытого имени. Сервер без ECH отклоняется; повторного подключения с открытым
внутренним SNI нет. Повреждённая/просроченная конфигурация не отправляет ClientHello.

Успешный ECH e2e пока не проверен. Python-сервер bProto не принимает ECH:
нужен совместимый управляемый frontend с поддержкой HTTP/3-транспорта.
Не реализованы DNS discovery, автоматическая ротация/retry, optional fallback.
Нужны проверки на Android-устройстве и принимающем сервере. ECH не скрывает
IP-адрес и не гарантирует обход белого списка или блокировки РКН.

При выборе Android-профиля с обязательным ECH автовыбор исключает серверы без ECH.
Повреждённый или просроченный кандидат завершается ошибкой, без обычного подключения.
